# Playwright E2E suite

End-to-end tests for the Soloclef web app, notebooks-first.
There are two targets and they never mix:

| Project | Runs against | May write? | Command |
|---|---|---|---|
| `desktop` (1280×800) | the isolated e2e stack | yes | `pnpm test:e2e` (both) or `pnpm test:e2e:desktop` |
| `phone` (390×844, touch, `isMobile`) | the isolated e2e stack | yes | `pnpm test:e2e` (both) or `pnpm test:e2e:phone` |
| `prod-smoke` | a production server, read-only | no | `PROD_BASE_URL=… PROD_E2E_TOKEN=… pnpm test:e2e:prod-smoke` |

`setup` (tests/auth.setup.ts) runs automatically before `desktop` and `phone`.

## The isolated stack

`scripts/e2e-stack-go.sh` runs the Go stack as a deployment runs it,
`docker/docker-compose.go.yml`, with `docker/docker-compose.e2e-web-go.yml`
laid over it, under its own compose project, `soloclefgo-e2e`. The overlay adds
only what a browser test needs:

- the API's test-only routes (`/__e2e__/auth/token`, `/__e2e__/seed/...`,
  `/__e2e__/mail/last`, ...), switched on there and nowhere else;
- a stand-in for the model proxy (`docker/e2e-web-go/model-stub/stub.py`):
  chat, the short jobs, embeddings and speech in the OpenAI shape;
- stand-ins for Nextcloud and Google (`docker/e2e-web-go/nextcloud-stub`,
  `docker/e2e-web-go/google-stub`), standard-library Python;
- Caddy with the deployment's own routes plus the three test-only ones
  (`docker/e2e-web-go/Caddyfile`);
- the frontend built from this checkout.

Only Caddy is published, on 127.0.0.1:3945 (`docker/e2e-web-go/settings.env`).
Everything else is on internal networks with no route out, so no test can
reach a paid provider or a real account. The settings file holds every value
the stack reads; the secrets are generated by the script and deleted by
`down`.

```bash
cd soloclef_web
pnpm install
pnpm test:e2e:install          # Chromium for Playwright, once
pnpm test:e2e:stack:up         # build images if missing, start, wait, seed the e2e user
pnpm test:e2e                  # desktop + phone
pnpm test:e2e:stack:down       # stop and delete containers, volumes, networks, secrets
```

After changing app code, `pnpm test:e2e:stack:rebuild` rebuilds every image
from this checkout and restarts the stack; `bash scripts/e2e-stack-go.sh
rebuild api frontend` rebuilds only the ones named.
`bash scripts/e2e-stack-go.sh status|logs [service]` for diagnostics.

## What is real and what is faked

Real: Postgres, Valkey, Qdrant, MinIO, the parser service, the indexer and the
worker, zero-cache, Caddy, the API's routes, permissions and persistence, the
frontend build, and every browser interaction. Nothing in the application has
a test-only branch: a fake is a stand-in at an address the stack already
calls.

| Flow | How it is covered |
|---|---|
| Chat answers | The model stub picks its reply from the last user message: `E2E_ANSWER` gives a fixed answer, `E2E_CITE:<chunk id>` an answer citing that chunk (the spec reads a real chunk id from the API). Streamed through the real chat route. |
| Follow-ups, welcome questions, Studio focus ideas, source guides | The model stub, told apart by the prompt's opening sentence; every string has "E2E" in it. |
| Embeddings | The model stub makes vectors from the text's own words, so a search finds the passage a spec just wrote. |
| Studio generation | The sandbox is switched off in the settings. Specs assert the dialog and the exact generate request. An Audio Overview goes the whole way (drafted, voiced with one short MP3, joined, stored). |
| Studio viewers | `POST /__e2e__/seed/studio-output` saves finished outputs as Studio does (real files in the bucket, document rows), for every kind and for running and failed states. |
| An answer looked at mid-stream | The stub answers at once, so `chat-steps-line.spec.ts` replaces the chat request in the browser with a stream the test pushes, in the API's event shapes; the reload reads the real thread. |
| Research search | The stack has no internet: the real API is used for the failure path; result lists come from a browser-side stub with the API's event shape. The import that follows is real. |
| Sources | Created as a user would: a note, then "Convert to source" (real document, real indexing). Uploads go through the real upload route and the real parser service. |
| Nextcloud and Google Drive | The stand-ins answer the sign-in, token and file calls; the API and the worker reach Google under its own names over TLS, with a certificate from the stack's own test authority. |

## Layout checks (phone)

`tests/helpers/layout/overflow.ts` runs after every page, dialog, sheet and
menu is opened (`expectNoOverflow(page, label)`):

- no horizontal document scroll (`scrollWidth <= clientWidth`);
- no visible element past the viewport's left/right edge, except inside an
  element that scrolls sideways on purpose (`overflow-x: auto|scroll`); content
  clipped by an `overflow: hidden` ancestor counts only where it shows;
- on phones, text inputs (inputs, textareas, contenteditables) are at least
  16px, so iOS does not zoom on focus;
- `expectHeaderClearsSafeArea(header)`: the notebook header is padded by
  `env(safe-area-inset-top)` (Chromium cannot emulate a notch, so this checks
  the CSS rule that applies to the header).

Failures are soft (the test continues and lists every offender with a selector
and its left/right edges). `tests/app/overflow-helper.spec.ts` proves the
checker catches what it claims to.

Every app test also fails on a native `alert`/`confirm`/`prompt` and on an
uncaught page error (tests/app/fixtures.ts).

## prod-smoke (read-only, production)

`tests/prod-smoke/read-only.spec.ts` navigates production, opens dialogs and
closes them, and runs the layout checks at both viewports. It never submits a
form. On top of that, `tests/prod-smoke/guard.ts` aborts, in the browser, every
request that is not GET/HEAD/OPTIONS, except these reads that the app
implements as POST:

- `POST /api/zero/query` (Zero query resolution);
- `POST /api/v1/messages/comments/batch` (comment counts for visible messages);
- `POST /api/v1/notebooks/<nb>/followups` (follow-up questions).

It also blocks two GETs that would spend model tokens and write a cache:
`/studio/suggestions` and `/sources/<id>/guide`. Blocked requests are attached
to each test's report as `blocked-writes`. (An app write that the guard
aborts, e.g. creating a chat for a notebook that has none, just fails in the
page; nothing reaches the server.)

```bash
PROD_BASE_URL=https://notes.example.com \
PROD_E2E_TOKEN=<access token for a real user> pnpm test:e2e:prod-smoke
```

Both are required. Optional: `PROD_NOTEBOOK_ID` (default: the notebook with the most
sources), `PROD_EXTRA_COOKIES="name=value; …"` (e.g. the SSO proxy's session
cookie in front of the app), `PROD_EXTRA_HEADERS='{"X-…":"…"}'`.

To dry-run it against the isolated stack:

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:3945/__e2e__/auth/token \
  -H 'Content-Type: application/json' \
  -H 'X-E2E-Mint-Secret: e2e-mint-secret-not-for-production' -d '{}' | jq -r .access_token)
PROD_BASE_URL=http://127.0.0.1:3945 PROD_E2E_TOKEN=$TOKEN pnpm test:e2e:prod-smoke
```

## Writing tests

- Import `test`/`expect` from `tests/app/fixtures.ts`; use the `notebook`
  fixture (fresh per test, deleted after) and `uniqueName()` for anything else
  you create. Every test signs in as the same account, so never assume the
  account is empty: assert on what the test made.
- Prefer roles and accessible names; add a `data-testid` only when there is no
  stable accessible name.
- Call `expectNoOverflow(page, "<what is open>")` after opening anything.
- Seed data through the real API (`tests/helpers/api/*`) or, for Studio outputs,
  `seedOutput()`.
- Known gap worth knowing: the automation builder still requires premium/BYOK
  image and vision models for creation (the API dropped that policy), so
  in this stack creation is checked as blocked and the detail/edit/delete flow
  starts from an automation created through the API.
